# current-status (Codex CLI판)

> **Codex CLI 전용 스킬이다** — 호출 형식(`$current-status [인자]`)과 제안의
> «다음 명령»이 Codex의 스킬 체계(`$HOME/.agents/skills`·`$스킬명` 호출·
> AGENTS.md 자동 로딩)를 전제한다. Claude Code 사용자는 저장소의
> `plugins/current-status` 쪽 SKILL.md를 사용할 것. 본문의 `/interview`·
> `/make-design`·`/make-plan`·`/execute`·`/verify`·`/milestone`은 각각
> `$interview`·`$make-design`·`$make-plan`·`$execute`·`$verify`·`$milestone`으로
> 읽는다.

> 이 스킬은 **세션의 첫 판단**이고 그 판단이 후속 작업 전체의 전제가 된다.
> 상위 모델·높은 reasoning effort로 실행할 것을 권장한다 — 판정이 틀리면 비용은
> 이 스킬이 아니라 잘못된 방향으로 간 사이클 전체가 치른다.

**지금 어디까지 왔고 다음에 무엇을 해야 하는가**를 판정한다. 기록 하나를 보여주는 조회
도구가 아니라, **여러 소스를 교차해 판단을 내리는** 도구다.

**읽기 전용이다.** 원장·기록·플랜·코드 어느 것도 수정하지 않는다. 제안한 작업을 실제로
하지도 않는다 — 사용자가 고르면 해당 스킬(`/interview`·`/make-design`·`/make-plan`·
`/execute`·`/verify`)로 넘긴다.

## 0. 이 프로젝트를 먼저 읽는다

전역 스킬이므로 어느 레포에서 호출될지 모른다. 프로젝트 지침 파일(`CLAUDE.md`·
`AGENTS.md`)에서 기록 체계(원장·결정 기록·작업 노트의 위치와 규약)와 표준 검사 명령을
파악한다. 프로젝트 규약이 있으면 이 스킬의 기본값을 이긴다.

## 1. 소스 — 무엇을 읽는가

있는 것만 읽되, **서로 독립이므로 한 번에 병렬로 읽는다.**

| 소스 | 무엇을 얻는가 |
|---|---|
| **작업 원장** (`kanban.md`·`workstate.md` 중 있는 쪽) | **지금 손대는 것의 정본.** 이 파일을 먼저 읽는다 — 나머지 소스는 이것을 **대조**하기 위해 읽는 것이다 |
| `backlog.md` (있으면) | 범위 밖의 열린 항목. **전문을 읽지 않는다 — 건수만 센다.** 순위 판정을 받지 않으므로 제안에 오르지 않는다. 여기서 항목을 주워 순위에 올리는 것이 백로그 분리가 막으려는 바로 그 동작이다 — 승격은 사용자가 정한다 |
| **`MILESTONE.md`** (있으면) | **활성 마일스톤의 목표·종료 조건·범위 표.** 순위의 기준선이다 — 범위 표에 없는 항목은 순위에 오르지 않는다(§3.1 G0). 없으면 「참고」에 `/milestone set`을 권하고 나머지는 그대로 진행한다 |
| 결정 기록 (devlog·`discussions/` 등 프로젝트 규약의 것) | 확정된 결정·배제·기각. 옛 항목에 붙은 "다음 할 일" 목록은 **그 시점의 히스토리**이지 현재 상태가 아니다 |
| 작업 노트 (devnote 등, 최신 파일) | 직전 작업의 미완 맥락·실패한 시도·아직 요약 기록에 안 올라간 진행 |
| `plans/*.md` — **먼저 상태 줄만 훑고, 걸린 것만 연다** (아래 명령) | 플랜·리포트별 상태(`초안` / `완료 (날짜)` / `중단 (날짜, 지점/사유)` — 어휘 정본은 `/make-plan` §3) |
| `plans/*-execute-report.md` · `*-verify-report.md` 중 상태가 **`진행 중`**인 것 | 중단된 사이클의 재개 지점. **원장 마지막 행이 실제로 도달한 지점이다** — 플랜 체크박스보다 이쪽이 정확하다 |
| 정본 설계 문서(아키텍처 문서 등)의 확정 절·미결 절 | 확정된 원칙과 **미결 항목** — 미결에 막힌 작업은 착수 불가 |
| `git log --oneline -15`, `git status --short` | 실제로 커밋된 것과 미커밋 변경분 |
| 실물 디렉터리 목록 (패키지·모듈) | 실제로 존재하는 것 (기록상 "구현 완료"와 대조) |

**`plans/`는 파일마다 열지 않는다.** 모집단은 **전수 그대로 두되** 읽는 방식을 바꾼다 —
상태 줄만 한 번에 훑고, `완료`가 아닌 것만 실제로 연다:

```bash
for f in plans/*.md; do s=$(head -10 "$f" | grep -m1 '상태:'); case "$s" in *완료*|"") ;; *) echo "$f  $s";; esac; done
```

- **줄 첫머리로 앵커하지 않는다** — 인터뷰 기록은 상태를 `- 일자: … · 상태: **결정됨**`
  처럼 줄 중간에 단다. 앵커하면 `결정됨` 인터뷰가 그물을 빠진다(실측: 같은 날의 확정
  결정을 못 보고 같은 물음을 다시 열어 전부 되돌린 전례). 머리 열 줄 안의 `상태:`를 전부
  본다.
- **모집단을 「최근 며칠」로 좁히지 않는다.** 이 대조가 잡으라고 있는 것이 *"어느 레인에도
  없는 미완 플랜"*이고, 그것은 **오래된 것일수록 위험하다.** 위 명령은 전수를 보면서도
  여는 것은 몇 개뿐이다.

**통합 게이트(테스트·린트)는 기본으로 실행하지 않는다** — 느리고, 게이트 상태는 최근
기록에 대개 적혀 있다. 사용자가 `full`/`전체`를 요청했을 때, 또는 미커밋 변경분이 있어
마지막 기록된 그린 상태를 믿을 수 없을 때만 실행한다.

## 2. 교차 검증 — 이 스킬의 핵심

기록 하나만 읽으면 놓치는 것들이 있다. **다음을 반드시 대조한다.**

- **원장은 손으로 갱신되므로 원장도 검증 대상이다.** 각 항목을 실물과 맞춰본다 —
  "진행 중" 항목의 플랜이 실제로 `완료`인지, "검증 대기" 항목이 가리키는 리포트가 이미
  소비됐는지, 어느 레인에도 없는 미완 플랜이 `plans/`에 있는지. **불일치를 발견해도
  원장을 고치지 않고 보고한다**(§6) — 원장이 실물보다 낡는 것은 예상된 실패 양태이고,
  그것을 잡는 유일한 수단이 이 대조다.
- **요약 기록은 세션 끝에 쓰고 작업 노트는 작업 중에 쓴다.** 세션이 중단되면 노트에만
  있고 요약에는 없는 진행이 생긴다. 노트의 마지막 섹션이 요약의 마지막 항목보다 나중
  시각이면 **그쪽이 최신**이다.
- **옛 기록의 체크박스를 현재 할 일로 읽지 않는다.** 열려 있는 것의 정본은 원장 하나뿐이다.
  옛 목록에 있는데 원장에 없으면 "누락"이 아니라 "그 사이에 닫혔다"가 기본 해석이다. 정말
  누락으로 의심되면 **불일치로 보고**하고, 항목을 만들지는 사용자가 정한다.
- **미결 항목이 다음 작업을 막고 있는지 본다.** 정본 문서의 미결 절에 남은 항목은 "결정
  없이 코드를 쓰기 시작하면 안 되는 것"이다. 제안하려는 작업이 미결에 걸려 있으면 그
  작업이 아니라 **설계(`/make-design`)가 다음 작업**이다.
- **상태가 `진행 중`인 리포트는 중단된 사이클이다.** 리포트는 착수 시점에 만들어져 종료
  시 닫힌다. `진행 중`으로 남아 있다면 세션이 끊겼다는 뜻이다 — **원장의 마지막 행이 실제
  도달 지점**이므로 재개 제안(`/execute … T-00x부터`)은 여기서 나온다.
- **미커밋 변경분이 있으면 무엇인지 확인한다.** 진행 중이던 작업의 흔적일 수 있다. 목록만
  보고 추측하지 말고 어느 영역인지(소스·문서·기록) 구분해 보고한다.

## 3. 다음 작업 제안 — 게이트 → 정렬 → 묶음

**없는 일을 발명하지 않는다.** 제안의 출처는 **원장의 항목**이다. 원장에 없는데 제안하고
싶은 것(정본 문서의 미결, 플랜의 미완 작업, 교차 검증에서 나온 불일치)은 **"원장에 없는
항목"이라고 표시**해 올린다 — 항목으로 만들지는 사용자가 정한다.

### 3.1 게이트 — 순위를 매기기 **전에** 걸러낸다

**남은 일의 대부분은 순위 문제가 아니라 착수 가능성 문제다.** 발동 조건이 명시된 채
의도적으로 미뤄진 항목에 중요도 점수를 매기는 것은 **이미 끝난 판정을 다시 여는 것**이다.

**G0 마일스톤 범위 — 세 게이트보다 먼저.** `MILESTONE.md`가 있으면 그 범위 표에 **없는**
항목은 아래 게이트에 태우지도 않고 「마일스톤 외」 표로 보낸다. 예외는 하나 — 범위 안
조건을 **직접** 블록하는 항목(예: 종료 조건의 게이트를 지금 깨뜨리는 것)은
«범위 밖·블로커»로 표시해 순위에 올린다. 애매하면 밖으로 두고 애매하다고 보고한다 —
편입은 `/milestone`의 범위 변경 절차다.

| 게이트 | 판정 기준 | 처리 |
|---|---|---|
| **G1 트리거 대기** | 항목에 `트리거는 ~`·`~할 때`처럼 발동 조건이 적혀 있고 아직 발동하지 않음 | 대기열로 분리. **트리거 문구를 그대로 인용**한다 — 요약하면 다음에 발동 여부를 못 잰다 |
| **G2 선행 블록** | 정본 문서의 미결이나 설계 문서 부재에 걸려 있음 | 그 항목 대신 **선행 설계**가 후보로 올라간다 (`/make-design`) |
| **G3 사용자 액션** | API 키·권한·외부 계정·수동 실행처럼 에이전트가 수행할 수 없음 | 별도 칸. 무엇을 해달라는 것인지 한 줄로 |

**게이트 판정은 근거를 밝힌다.** 특히 G1은 "발동했다"고 판정할 때가 위험하다 — 트리거
문구와 지금 관측된 사실을 나란히 놓고 대조한 결과를 쓴다. 애매하면 대기로 두고 **판정이
애매하다는 사실 자체를 보고**한다.

### 3.2 정렬 — 게이트를 통과한 것만

**기록의 명시가 추론을 이긴다.** 기록에 `(다음 최우선)` 같은 표시가 있으면 그것이
1순위이고 아래 축을 계산하지 않는다. 표시가 없을 때만 판단하고, **판단했다는 사실과
근거를 밝힌다.**

네 축을 본다. 점수를 합산하지 말고 **어느 축이 그 항목을 올렸는지 이름을 대며**
정렬한다 — 합산은 근거를 지운다.

- **A. 하류 레버리지** — 이후 작업이 이것 위에 서는가. 게이트·계약·설계 > 단발 수정
- **B. 틀렸을 때의 정정 비용** — 계약·강제 수단이 틀리면 그 위에 쌓인 것까지 오염된다.
  A와 다르다 — A는 "얼마나 많이 의존하는가", B는 "틀린 채로 얼마나 오래 안 드러나는가"
- **C. 착수 비용** — 진입 비용(어느 문서·코드를 열어야 하는가)과 **검증 비용**(전체
  스위트인가, 단일 테스트인가)을 나눠 본다
- **D. 묶음 이득** — §3.3에서 쓴다. 개별 점수로는 보이지 않는 축이다

**E. 항목이 열려 있던 기간은 순위 축이 아니라 재판정 트리거다.** 생성 후 3사이클
이상이면 순위를 올리지 말고 **"할 것인가 / 닫을 것인가"를 별도 항목으로 묻는다.** 오래
밀렸다는 것은 중요하다는 신호가 아니라 대개 범위가 잘못 잡혔거나 실은 안 해도 되는
일이라는 신호다.

### 3.3 묶음 — 이번 사이클을 어떻게 구성하나

순위만 내면 사용자가 매번 "그럼 이번에 뭘 같이 하지"를 다시 판단해야 한다. **한 사이클
분량의 묶음을 하나 제안한다.**

**묶음의 근거는 셋 중 하나여야 한다. 없으면 묶지 않는다** — 근거 없는 묶음은 나열이다.

1. **같은 파일·문서를 연다** — 진입 비용을 1회로 만든다
2. **검증 비용을 공유한다** — 같은 전체 스위트 1회로 함께 검증된다
3. **기록이 이미 묶어 뒀다** — "셋 다 작고 서로 독립" 같은 명시

**크기 상한** — 서로 독립인 소형 3~4건, 또는 대형 1건. 소형과 대형을 섞지 않는다(대형이
미끄러지면 소형까지 함께 밀린다).

**묶음은 제안이지 플랜이 아니다.** 작업 순서·검증 조건·롤백은 `/make-plan`이 정한다.
여기서는 "무엇을 함께"까지만 낸다.

### 3.4 각 제안에 붙이는 것

이게 없으면 제안이 아니라 나열이다:

- **원장 항목 ID** — 원장에 없는 항목이면 `(원장에 없음)`이라고 쓴다
- **왜 지금인가** — 어느 축이 이걸 올렸는지(A/B/C/D 중), 무엇을 블록하고 있거나 무엇이
  준비돼서 지금 가능한지
- **정본 문서** — 그 작업의 계약이 어디 있는지(경로 + §번호). 정본이 아직 없다면 그 사실
  자체가 설계가 먼저라는 신호다
- **권장 모델** — 복잡도 근거 한 줄과 함께 (규칙은 §3.5)
- **다음 명령** — `/<스킬> <대상 경로>` 한 줄 (규칙은 §3.5). 방향 미확정이면
  `/interview`, 미결이면 `/make-design`, 설계가 확정됐고 플랜이 없으면 `/make-plan`,
  플랜이 있으면 `/execute`(중단된 사이클이면 `T-00x부터`), 구현물 감사면 `/verify`

### 3.5 다음 명령 표기 규칙 (모든 제안에 적용)

제안의 실행 경로는 **복붙 가능한 한 줄**이어야 한다. 형식은 고정한다:

```
권장 모델 — <상위|중위|하위> · <복잡도 근거 한 줄>
$<스킬명> <대상 파일 경로>
```

- **스킬명만 쓰지 않는다.** 대상 없는 제안은 사용자가 "어느 플랜이었지"를 다시 찾게
  만든다 — 작업 흐름이 끊기는 지점이 정확히 여기다.
- 경로는 **프로젝트 루트 기준 전체 상대 경로.** 문서의 일부면 `§번호`, 아직 없는 파일이면
  `(신규)` — 그 명령이 만들 파일이라는 뜻이다.
- 진행 중이던 플랜을 이어받는 경우 **재개 지점까지** 쓴다:
  `/execute plans/YYYYMMDD-<주제>-plan.md T-005부터`
- **경로는 실제로 존재하는지 확인하고 쓴다**(`(신규)` 제외). 기억으로 쓴 경로가 틀리면
  다음 세션이 잘못된 파일을 연다. 스킬명도 그 프로젝트에 실재하는 이름인지 확인한다.

**권장 모델 판정** — 스킬 이름이 아니라 **다음 작업의 복잡도**로 한다 (이 규칙이 체인
전체의 정본이다 — `/make-design`·`/make-plan`·`/execute`·`/verify`의 «다음 명령» 절이
이것을 따른다):

- **상위** (또는 reasoning effort 상향) — 열린 결정을 닫거나 되돌리기 어려운 것을 만드는 작업: 미결이 걸린 설계, 여러
  문서·패키지에 걸치는 구현, 실패 판정이 나올 수 있는 검증, 원인 불명 디버깅
- **중위** — 계약이 확정돼 있어 따라가면 되는 작업: 플랜이 명확한 실행, 정본 §번호가
  특정된 검증, 확정 설계의 플랜 작성
- **하위** — 판단 없이 기계적으로 끝나는 작업: 기록·조회, 경로 치환 수준의 수정
- 경계에 걸리면 **오류 비용이 큰 쪽(위 단계)** — 모델을 낮춰 아끼는 것보다 잘못 판정된
  사이클을 되돌리는 것이 비싸다
- 대상 스킬의 frontmatter에 `model:`이 박혀 있으면 그 값이 곧 권장이다
- 권장이 현재 세션 모델과 다르면 `/model` 전환을 함께 안내한다

순위 목록은 **3개 이내**로 좁힌다. 게이트에 걸린 항목은 이 3개에 포함되지 않으며 개수
제한 없이 표로 낸다.

## 4. 출력 형식

터미널 마크다운. 표는 짧고 열거 가능한 사실에만 쓰고 판단은 산문으로 쓴다.

```
## <프로젝트> 현황 — YYYY-MM-DD 기준

### 지금 위치
<한두 문단. 마지막으로 무엇이 끝났고 무엇이 열려 있는지.>

### 마일스톤   ← MILESTONE.md 없으면 생략
M1 · <이름> · 남은 조건 N개 — <미달 조건 이름만>. (검증 줄을 실제 실행해 센다)

### 진행 상태
| 영역 | 상태 | 근거 |
|---|---|---|

### 원장과 실물의 차이   ← 없으면 생략
<불일치가 있을 때만. 어느 항목이 어긋났고 어느 쪽이 맞는지. 고치지는 않는다.>

### 다음 작업 제안
**1. <항목 ID> <제목>**
왜 지금 — <축 이름 + 근거>
정본 — <경로 §번호>
권장 모델 — <상위|중위|하위> · <근거>
다음 명령 — `$<스킬> <경로>`

### 이번 사이클 묶음 제안   ← 근거를 못 대면 생략하고 1순위 단독
<왜 함께인지(같은 파일 / 검증 비용 공유 / 기록이 묶음) 한 줄.>

### 지금 실행할 명령
<1순위(또는 묶음)의 명령 한 줄. 보고의 마지막 줄이 항상 이것이고, 권장 모델 줄을 그
바로 위에 붙인다.>

### 마일스톤 외 — 순위 없음   ← 해당 없으면 생략
### 트리거 대기 — 순위 없음   ← 해당 없으면 생략 (트리거 원문 + 지금 발동했나)
### 사용자 액션 대기   ← 없으면 생략
### 재판정 필요 — 생성 후 3사이클 이상   ← 없으면 생략
### 참고
<마지막 기록이 오늘이 아니면 며칠 전인지. 미커밋 변경분이 있으면 그 사실.
백로그 건수 한 줄.>
```

## 5. 인자별 동작

인자는 `$1`로 들어온다.

| 인자 | 동작 |
|---|---|
| (없음) | 위 전체 형식 |
| `next`, `다음` | "다음 작업 제안"만. 소스는 똑같이 다 읽되 출력만 좁힌다 |
| `priority`, `우선순위`, `뭐부터` | §3 전체 — 게이트 분류·순위·묶음·트리거 대기·재판정. "진행 상태" 표는 생략 |
| `board`, `보드`, `원장` | 원장 항목 목록 + 원장↔실물 대조 결과만. 순위·묶음은 생략 |
| `plan`, `플랜` | 플랜 문서 상태표 + 각 플랜의 미완 작업 |
| `design`, `설계` | 정본 문서의 확정/미결 대비표 |
| `full`, `전체` | 전체 + 통합 게이트 실행 결과 |
| 그 외 문자열 | 그 주제에 한정한 현황과 다음 작업 |

## 6. 하지 않는 것

- **어떤 파일도 쓰지 않는다 — 작업 원장도 포함이다.** 원장이 실물과 어긋나 있어도 고치지
  않고 보고한다. 항목을 만들거나 옮기는 것은 작업을 실제로 하는 스킬의 일이고, 여기서
  고치면 **일어나지 않은 작업이 원장에 기록된다.**
- **제안한 작업을 바로 시작하지 않는다.** 사용자가 고르기 전에 설계·구현에 들어가지
  않는다.
- **읽지 않은 것을 추측하지 않는다.** 소스에 근거가 없으면 "기록에 없다"고 쓴다.
  레퍼런스를 뒤져 "이런 게 필요할 것"이라고 만들어내지 않는다 — 그건 설계 작업이고
  `/make-design`이 한다.
- **트리거 대기 항목을 순위에 올리지 않는다.** 발동했다고 판정하려면 **관측된 사실**을
  트리거 문구와 나란히 제시한다. 근거 없이 끌어올리는 것은 확정된 보류 판정을 뒤집는
  것이다.
- **묶음을 플랜으로 키우지 않는다.** "무엇을 함께"까지가 이 스킬이고, 작업 순서·검증
  조건·롤백은 `/make-plan`이 정한다.
- **진척을 평가하지 않는다.** "순조롭다", "속도가 느리다" 같은 총평은 쓰지 않는다. 상태와
  다음 작업만 낸다.
- **과거 기록의 판단을 고치지 않는다.** 지난 결정이 지금 보기에 틀렸어도 현황에는 "그때
  이렇게 결정됨"으로 적고, 재논의가 필요하면 그것을 제안 항목으로 올린다.

## 전제

interview→make-design→make-plan→execute→verify 체인의 관제 지점 — 각 스킬이 사이클을
닫으며 "다음 작업 후보 조회"로 넘길 때의 수신처다. 작업 원장(`kanban.md`·`workstate.md`)
이 있으면 가장 잘 동작하고, 없으면 plans/·git·정본 문서만으로 판정하되 원장 신설을
권한다. `MILESTONE.md`가 있으면 `/milestone`의 범위 표를 순위 기준선(G0)으로 쓴다.
