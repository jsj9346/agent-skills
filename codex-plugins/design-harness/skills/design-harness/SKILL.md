# Design Harness — 목적 맞춤형 작업 환경 설계 (Codex CLI판)

> **Codex CLI 전용 스킬이다** — 절차가 Codex의 구성 요소(AGENTS.md·
> `$HOME/.agents/skills`·approval/sandbox 정책)를 전제한다. Claude Code
> 사용자는 저장소 루트의 SKILL.md를 사용할 것.

> 지침(AGENTS.md)은 "무엇을 하라"고 말하고, harness는 그것이 실제로 지켜지게
> 만든다(도구·강제·검증). 이 스킬은 그 harness를 **Gap만 채우는 최소 형태**로
> 설계한다.

> Harness는 많을수록 좋은 것이 아니다. 파일 하나가 늘 때마다 컨텍스트 비용·
> 유지보수·규칙 충돌 가능성이 같이 는다. 이 스킬의 성공 기준은 "얼마나 많이
> 만들었나"가 아니라 **"프로젝트와 모델에 맞는 가장 작은 harness를 찾았나"**다.

## 필수 하네스 4종 — 기본 골격

어떤 체급·어떤 프로젝트든, 설계 결과에는 아래 4종이 반드시 포함되어야 한다.
이 4종은 Gap 분석의 결과가 아니라 **전제**다: **존재는 필수**이고, **내용은
Gap 분석으로 최소화**한다. 하나라도 없으면 설계는 미완이다.

| 하네스 | 정본 | 역할 |
|---|---|---|
| **정책 하네스** | `AGENTS.md` | 모델이 **무엇을 지켜야 하는지** 정의 |
| **절차 하네스** | `PROTOCOL.md` | **어떤 순서와 조건으로** 작업해야 하는지 정의 |
| **검증 하네스** | 테스트 · 린트 · CI | 결과물이 **기준을 만족하는지** 강제 |
| **상태 하네스** | `WORKSTATE.md` | **현재 어디까지 진행됐는지** 유지 |

- 4종의 정본 파일은 파일 예산(원칙 5)에 넣지 않는다 — 골격이지 추가 항목이
  아니다.
- **얇은 것은 정상, 없는 것은 결함이다.** 체급 S라면 각각 몇 줄이면 되고,
  검증 하네스는 CI 없이 로컬 테스트·린트 명령 하나로 시작해도 된다.
- 역할 경계를 지킨다: 정책(무엇을 지키나) / 절차(어떤 순서로 하나) / 검증
  (기준을 만족했나) / 상태(어디까지 왔나). 한 내용이 두 하네스에 걸치면 역할
  단일성(원칙 4) 위반이다 — 정본 한 곳을 정하고 나머지는 참조만 한다.

## 원칙 (하드 레일)

1. **Gap 없는 항목 금지** — 모든 harness 항목은 "어느 Gap을 채우는가"를
   명시해야 한다. 모델이나 런타임이 이미 하는 일이면 항목이 될 수 없다.
   예외: 필수 하네스 4종의 **존재**는 Gap 분석 없이 보장한다 — 단 그 안에
   담기는 **내용**은 이 원칙을 그대로 따른다.
2. **토대 검증** — "런타임이 이걸 해준다/안 해준다"는 추정 금지. 실제 문서·
   설정·동작으로 확인한 것만 인벤토리에 적는다. 확인 못 했으면 "미확인"으로
   표기한다.
3. **실측 근거** — 항목의 근거는 둘 중 하나여야 한다: (a) 이 프로젝트에서
   **관측된** 실패·반복·요구, (b) 사용자가 명시한 **Invariant**(비가역·치명).
   "혹시 몰라서", "일반적으로 좋다고 알려져서", "나중에 필요할 수 있어서"는
   근거가 아니다 — 아직 발생하지 않은 실패에 대한 예방 항목은 (b)일 때만
   허용한다.
4. **역할 단일성** — 하나의 역할(예: 커밋 전 테스트, 배포 명령 차단, 마이그레이션
   절차)은 harness 전체에서 **정확히 한 곳**에만 산다. 같은 역할을 AGENTS.md·
   스킬·approval 정책에 나눠 놓거나, 비슷한 이름의 스킬을 둘 만들지 않는다.
   지침을 강제층으로 승격하면 지침에서는 **제거**한다. 새 파일은 기존 파일
   (AGENTS.md·기존 스킬·설정)에 흡수할 수 없을 때만 만든다.
5. **파일 예산** — 신규 파일 수는 §3-b의 체급이 정하는 상한 안에서만 허용한다.
   상한을 넘기려면 파일 하나마다 사용자 승인을 따로 받는다. 필수 하네스 4종의
   정본 파일은 예산에서 제외한다. **0개 생성**(기존 파일 수정만, 또는 아무것도
   안 함)도 정상적인 결과다 — 단, 필수 4종이 없는 프로젝트에서는 그 4종을
   갖추는 것이 최소 산출물이다.
6. **체급 맞춤** — harness의 크기는 프로젝트 규모·개발 단계·팀 구성·개발 방향과
   실행 모델의 실측 특성에 맞춘다. 작은 프로젝트에 큰 harness를 붙이는 것은
   과최적화이며 결함으로 보고한다.
7. **모델 의존 표식** — 특정 모델의 약점을 보완하는 항목에는 `[model:<이름>]`
   표식을 단다. 이 표식 항목은 **이 프로젝트에서 그 모델이 실제로 보인 약점**에
   한한다(일반론적 "LLM은 ~를 못한다" 금지). 모델이 바뀌면 이 표식 항목만
   재검토하면 되게.
8. **Minimal 시작** — 확신 없는 항목은 빼고 시작한다. 규칙은 추가보다 제거가
   기본 방향이며, 설계안에는 항상 제거 후보와 **만들지 않기로 한 항목**을 함께
   보고한다.
9. **승인 후 생성** — 설계안 제시 → 사용자 승인 → 파일 생성. 기존 파일을
   덮어쓸 때는 반드시 diff를 먼저 보여준다.

## 절차

### 1. 목적 인터뷰

사용자에게 묻는다 (도메인에 맞게 적응형으로, 한 번에 몰아서):

- **목적**: 이 프로젝트/워크스페이스는 무엇을 하는 곳인가?
- **실패 모드**: 무엇이 잘못되면 가장 아픈가? (도메인마다 다름 — 코딩=회귀·
  보안, 분석=오염된 데이터, 기록=원본 훼손) **실제로 겪은 것**과 **우려**를
  구분해서 받는다.
- **완료 판정**: 무엇을 만족하면 "됐다"고 판단하는가? 검증 가능한 형태로.
- **Invariants**: 절대 일어나면 안 되는 것은? (여기서 나온 것만 지침층에 들어간다)
- **우선순위**: Accuracy / Cost / Speed 중 무엇이 중요한가?
- **프로젝트 프로파일**: 규모(파일·모듈·서비스 수), 개발 단계(실험/초기/
  안정/유지보수), 팀 구성(1인/소규모/다중 팀), 개발 방향(앞으로 무엇이 늘고
  무엇이 굳어지는가), 주로 쓰는 모델과 런타임. — §3-b 체급 결정의 입력이다.

사용자가 답하지 못하는 항목은 비워 둔다 — 지어내지 않는다. 비워진 항목이
많을수록 harness는 얇아지는 게 맞다.

### 2. 기존 능력 인벤토리

셋을 **실제로 읽고** 목록화한다:

- **기존 프로젝트 설정**: AGENTS.md(저장소·상위 폴더 포함), 프로젝트/사용자
  스킬(`$HOME/.agents/skills` 등), Codex 설정 파일, CI 설정, 테스트 러너.
  각 파일마다 **"이 파일의 역할"을 한 문장**으로 적어 역할 목록을 만든다 —
  §3-c 역할 중복 검사의 기준선이다.
- **런타임 기본기**: 현재 Codex CLI가 기본 제공하는 것 — sandbox·approval
  모드·AGENTS.md 자동 로딩·skills 시스템 등. 버전에 따라 다르므로 이번
  세션에서 확인 가능한 것 기준으로 적고, 확인 못 한 것은 "미확인" 표기.
- **모델 기본기**: 현재 모델이 지시 없이도 잘하는 것(계획·자체 검토·도구 사용
  등)과 **이 프로젝트에서 실제로 관측된 약점**. 과소평가해 재교육 규칙을
  만들지 않고, 관측되지 않은 약점을 가정해 보완 규칙을 만들지도 않는다.

### 3. Gap 분석 → 체급 → 배치

#### 3-a. Gap 표

표로 강제한다:

| 작업 요구 | 근거(관측/Invariant) | 모델이 함? | 런타임이 함? | 기존 설정에 있음? | → Gap |
|---|---|---|---|---|---|

- Gap 열이 빈 행은 harness 항목이 될 수 없다.
- 근거 열이 "관측"도 "Invariant"도 아닌 행은 **보류 목록**으로 보낸다(원칙 3).
- 역방향도 본다: 기존 설정 중 모델·런타임과 **중복**인 규칙, 서로 **역할이
  겹치는** 파일은 제거·병합 후보 목록에 올린다.

#### 3-b. 체급 결정

프로젝트 프로파일과 Gap 수로 체급을 정하고, 신규 파일 상한을 확정한다.
기본값이며 사용자가 명시적으로 바꿀 수 있다:

| 체급 | 신호 (대체로 해당) | 신규 파일 상한 |
|---|---|---|
| **S** | 1인, 실험/초기 단계, 단일 언어, CI 없음, 비가역 Invariant 0~1 | 필수 4종만(각각 짧게 — AGENTS.md 몇 줄, PROTOCOL.md 몇 줄, 로컬 테스트·린트 명령, WORKSTATE.md 골격). 스킬·스크립트 없음. 강제가 꼭 필요한 Invariant는 approval/sandbox 설정 편집으로 |
| **M** | 소규모 팀 또는 CI 있음, 검증 가능한 완료 판정, 비가역 Invariant 존재, 반복 워크플로우 1~2개 | 필수 4종 + 신규 ≤ 2 (스킬·스크립트·CI 게이트 합산) |
| **L** | 다중 팀/서비스, 규제·보안 요건, 다중 언어, 반복 워크플로우 다수, 관측된 실패 이력 | 필수 4종 + 신규 ≤ 5. 초과분은 파일별 승인 |

- 상한은 **신규 파일** 기준이다. 기존 파일 수정은 예산에 넣지 않되, 역할 단일성
  검사는 동일하게 받는다.
- 체급이 애매하면 **낮은 쪽**을 고른다. 나중에 올리는 비용이 내리는 비용보다
  싸다.

#### 3-c. 배치 — Gap 하나에 집 하나

각 Gap에 **정확히 하나의** 층·파일을 배정한다. 충분한 수단 중 **가장 가벼운
것**을 고른다:

```
기존 파일에 한 줄 추가  >  AGENTS.md 한 줄  >  기존 테스트·린트로 검증
  >  스킬/스크립트(반복 워크플로우일 때만)
  >  approval·sandbox 정책·CI 게이트(강제가 필수일 때만)
```

- 예외: 비가역·치명 Invariant는 강제층이 기본이다. 지침만으로 두면 "왜
  강제하지 않는가"를 적는다. 단, 2단계 인벤토리에서 확인된 런타임 강제
  수단만 쓴다.
- **병합 규칙**: 트리거가 같거나(예: 커밋 전), 대상이 같거나(예: 마이그레이션),
  역할이 같은 항목은 한 파일로 합친다. 한 목적을 여러 스킬로 쪼개지 않는다.
- **역할 중복 검사**: 새 항목의 역할 한 문장을 §2의 기존 역할 목록과 대조한다.
  같거나 포함 관계면 신규 생성 대신 기존 파일 수정 또는 기존 파일 제거로
  처리한다.
- **필수 4종 우선 배치**: 절차(순서·조건) 항목은 PROTOCOL.md에, 진행 상태
  항목은 WORKSTATE.md에 배치한다 — AGENTS.md에 절차·상태를 섞지 않는다
  (역할 단일성).

### 4. 설계안 제시 (6층 + 파일 매니페스트)

필수 하네스 4종을 골격으로 놓고, 나머지는 Gap만으로 구성하며, 각 항목에
채우는 Gap을 주석으로 단다:

- **지침층 = 정책 하네스** — AGENTS.md: 모델이 무엇을 지켜야 하는지 — 그
  프로젝트의 Invariants만. 일반적인 작업 방법을 다시 가르치지 않는다.
- **절차층 = 절차 하네스** — PROTOCOL.md: 어떤 순서와 조건으로 작업해야
  하는지 — 단계 순서·단계 전이 조건·중단/재개 규칙. 정책(무엇을 지키나)과
  섞지 않는다.
- **도구층** — 스킬·스크립트: 반복 워크플로우. 두 번 이상 반복이 **관측된**
  것만.
- **강제층** — 지침이 어겨질 수 *없게* 만드는 부분. 2단계 인벤토리에서 확인된
  런타임 강제 수단(approval 정책·sandbox 설정·CI 게이트 등)만 쓴다.
  Invariant 중 강제 가능한 것은 지침층에만 두지 말고 여기로 승격을 검토한다
  (승격하면 지침층에서 제거).
- **검증층 = 검증 하네스** — 테스트·린트·CI·완료 판정 절차: 결과물이 기준을
  만족하는지 강제한다. 기존 검증 수단이 있으면 새로 만들지 않고 연결만 한다.
- **상태층 = 상태 하네스** — WORKSTATE.md: 현재 어디까지 진행됐는지 — 진행 중
  작업·완료/미완 경계·다음 단계를 유지해 세션이 끊겨도 이어받을 수 있게 한다.

설계안에는 반드시 **파일 매니페스트**를 붙인다:

| 파일 | 신규/수정 | 층 | 역할 (한 문장) | 채우는 Gap | 기존 파일로 안 되는 이유 |
|---|---|---|---|---|---|

그리고 함께 보고한다:

- **체급과 예산 대비 수치**: "체급 M, 신규 2/2".
- **역할 중복 검사 결과**: 겹침 없음, 또는 병합·제거한 내역.
- **제거 후보**: 기존 설정 중 모델·런타임과 중복이거나 역할이 겹치는 것.
- **보류 목록**: 만들지 않기로 한 항목과 그 이유(근거 부족·체급 초과·모델이
  이미 함). 나중에 관측이 쌓이면 다시 꺼낼 수 있게 남긴다.

### 5. 적합성 감사 → 검증 설계 → 생성

파일을 만들기 **전에** 두 가지를 통과한다.

**(1) 적합성 자체 감사** — 하나라도 실패하면 설계안으로 돌아간다:

- [ ] 필수 하네스 4종(정책·절차·검증·상태)이 모두 배치되었는가? 각 하네스의
      역할 경계가 서로 침범하지 않는가?
- [ ] 모든 항목이 관측된 요구 또는 명시된 Invariant에 근거하는가?
- [ ] 각 파일의 역할이 한 문장으로 적히고, 다른 파일과 겹치지 않는가?
- [ ] 신규 파일 수가 체급 상한 이내인가? (초과분은 파일별 승인을 받았는가?)
- [ ] 각 Gap이 가장 가벼운 충분 수단에 배치되었는가?
- [ ] `[model:]` 항목이 이 프로젝트에서 실측된 약점만 다루는가?
- [ ] 모델·런타임이 이미 하는 일을 다시 지시하는 항목이 없는가?
- [ ] 프로젝트 개발 방향(무엇이 늘고 무엇이 굳어지는가)과 어긋나는 항목이
      없는가?

**(2) 검증 설계** — 그 harness 자체의 평가 기준을 사용자와 확정한다:

- **판정 신호**: 이 harness가 작동한다/능률을 올린다를 무엇으로 관측하는가?
- **Kill Criteria**: 무엇이 보이면 규칙을 줄이거나 되돌리는가?
  (증상 예: 규칙 중복·충돌 발견, 같은 지시의 반복, 세션 체감 둔화, 유지보수
  부담 > 절감분, 만든 스킬·스크립트가 N주간 한 번도 안 쓰임, harness 파일
  수가 체급 상한을 넘어감)
- **재검토 시점**: 언제 다시 보는가? (모델 교체 시 `[model:]` 표식 항목은 자동
  재검토 대상. 개발 단계가 바뀌면 체급 재산정)

승인 후 파일을 생성하고, 생성·수정한 파일 목록과 각 파일이 채우는 Gap,
최종 예산 대비 수치를 보고한다.

## 과잉 harness 신호

설계안이나 기존 설정에서 다음이 보이면 즉시 병합·제거 대상으로 보고한다:

- 같은 규칙이 AGENTS.md와 스킬(또는 approval 정책)에 동시에 있다.
- 한 목적이 여러 스킬로 쪼개져 있다 (`test`, `test-unit`, `test-e2e` …가
  각각 한 줄짜리).
- 프로젝트에 없는 도구·언어·워크플로우를 위한 규칙·스킬이 있다.
- 파일 이름만 다르고 역할이 겹치는 문서가 둘 이상이다.
- 절차 규칙이 AGENTS.md와 PROTOCOL.md 양쪽에 있거나, 진행 상태가 WORKSTATE.md
  밖 여러 문서에 흩어져 있다 (필수 4종의 역할 경계 침범).
- 근거 열이 "일반적으로 좋다"인 항목, 미래 대비용 항목.
- 모델이 지시 없이도 하는 일(계획·자체 검토·테스트 실행)을 다시 지시하는 규칙.
- README·기존 문서에 이미 있는 내용을 AGENTS.md에 복제한 것.
- 체급 S 프로젝트에 스킬·스크립트·정책 파일이 여럿 있다.

## 산출물이 아닌 것

- 이 스킬은 도메인 지식을 대신 공급하지 않는다 — 실패 모드·완료 판정은
  사용자(도메인 이해자)의 답에서 온다. 답이 없으면 harness도 얇아지는 게 맞다.
- 범용 베스트 프랙티스 모음을 붙여넣지 않는다 — Gap 분석을 통과한 것만 쓴다.
- "완전한" harness를 목표하지 않는다 — 지금 관측된 것에 맞는 harness를 만들고,
  나머지는 보류 목록에 남겨 관측이 쌓였을 때 다시 본다.
