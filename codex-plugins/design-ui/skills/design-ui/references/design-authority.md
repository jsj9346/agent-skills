# 디자인 정본 판단 규칙

UI 구현 전에 무엇을 시각적 근거로 삼고 `DESIGN.md`를 만들거나 바꿀지 판단할 때 읽는다.
이 문서는 제품이 어떻게 보여야 하는지를 다룬다. 시스템 경계나 API 계약을 정하는 설계
문서를 대신하지 않는다.

## 근거 우선순위

아래 순서에서 숫자가 작은 근거가 우선한다.

1. 현재 사용자의 명시적 요구와 승인된 작업 범위
2. 대상 저장소의 `AGENTS.md` 및 프로젝트 지침
3. `DESIGN.md` 또는 같은 역할을 하는 프로젝트 디자인 문서
4. 디자인 토큰과 공용 컴포넌트 계약
5. 현재 렌더링된 제품과 기존 UI 코드에서 반복 확인되는 패턴
6. 이번 작업에 첨부된 Screenshot, Url, Figma, ExistingUi, Moodboard 참고물
7. 일반적인 디자인 휴리스틱

상위 근거가 기존 정본 변경을 요구할 수는 있지만, 하위 근거와의 충돌을 조용히
덮어쓰지는 않는다. 다음처럼 처리한다.

- 상위 근거가 명확하고 변경이 승인 범위 안이면 그 근거를 따르고, 바뀌는 정본과 영향을
  기록한다.
- 프로젝트 지침과 사용자 요구가 충돌하거나 제품 방향을 바꿀 선택이 필요하면 구현 전에
  `Design conflict`로 드러내고 확인을 받는다.
- 코드와 렌더링이 정본과 다르면 반복된 구현을 새 규칙으로 간주하지 않는다. 의도인지
  결함인지 구분한다.
- 참고물은 구조, 간격, 위계, 밀도, 행동을 위한 근거다. 사용자가 명시하지 않은 브랜드,
  문구, 에셋을 자동 복제하지 않는다.
- 접근하지 못한 URL·Figma와 보이지 않는 화면 상태·breakpoint는 추측하지 않고
  `Reference blocked` 및 미확인으로 기록한다.

## 같은 역할의 문서를 먼저 찾는다

루트와 관련 하위 경로에서 디자인 시스템, 스타일 가이드, 토큰 문서처럼 제품 시각 규칙의
정본 역할을 이미 하는 문서를 찾는다. 파일명이 다르다는 이유만으로 별도 `DESIGN.md`를
만들지 않는다. 기존 문서가 있다면 그 위치와 적용 범위를 확인해 먼저 사용한다.

## 네 가지 상황별 동작

| 상황 | 동작 |
|---|---|
| 디자인 정본이 존재 | 먼저 읽고 준수한다. 새 재사용 패턴이 확정될 때만 적용 범위와 이유를 적어 갱신한다. 기존 토큰·규칙으로 충분하면 파일을 바꾸지 않는다. |
| greenfield 또는 여러 화면에 적용될 새 시각 체계 | 구현 전에 루트 `DESIGN.md`를 최소 형태로 만든다. 현재 작업에서 실제로 결정된 규칙만 기록한다. |
| 기존 제품의 국소 수정 | 기존 토큰·컴포넌트로 충분하면 새 문서를 만들지 않는다. 일회성 위치·픽셀 값은 코드에만 두고 정본으로 승격하지 않는다. |
| 기존 제품인데 정본이 없고 새 패턴이 필요 | 구현 전에 `DESIGN.md`를 만들되, 코드와 렌더링에서 관측한 사실과 이번 작업에서 새로 결정한 규칙을 분명히 구분한다. |

새 문서가 필요할 때는 [`../assets/DESIGN.template.md`](../assets/DESIGN.template.md)를
복사해 프로젝트에 맞게 채운다. 모든 항목을 억지로 발명하지 말고 미확정 사항은
`Unresolved assumptions`에 남긴다.

## 디자인 시스템으로 승격하는 기준

규칙을 `DESIGN.md`에 올리는 것은 재사용 계약을 만드는 일이다. 다음을 모두 만족할 때
승격한다.

- 둘 이상의 화면·컴포넌트에서 재사용되거나 가까운 후속 작업에서 재사용할 것이 명확하다.
- 의도가 사용자 요구, 프로젝트 정본, 토큰 계약 중 하나로 확인되었거나 이번 범위에서
  명시적으로 결정되었다.
- 토큰, 컴포넌트, 레이아웃, 상태 또는 반응형 규칙으로 반복 적용할 수 있다.
- 적용 범위와 예외를 다른 구현자가 오해 없이 구분할 수 있다.

다음은 승격하지 않는다.

- 한 화면에만 필요한 일회성 픽셀 값이나 위치 보정
- 브라우저·프레임워크 구현 우연
- 참고물의 보이지 않는 부분을 추측한 규칙
- 의도가 확인되지 않은 기존 코드의 불일치
- 이번 작업에서 채택하지 않은 선택지와 장래 가능성

정본을 갱신했다면 최종 보고에 변경 이유, 추가·수정한 규칙, 영향을 받는 화면이나
컴포넌트, 남은 예외를 적는다.
