# Design Loop — 목표 실행 루프 설계

> **Claude Code 전용 스킬이다** — 산출 명령어가 Claude Code의 `/goal` 문법과
> `+Nk` 토큰 지시자를 전제한다. Codex CLI 사용자는 변형판
> [codex/SKILL.md](codex/SKILL.md)를 사용할 것.

> [design-harness](https://github.com/jsj9346/design-harness)가 **한 Node가
> 일을 잘하게**, [design-graph](https://github.com/jsj9346/design-graph)가
> **여러 Node가 함께 일을 잘하게** 만든다면, 이 스킬은 **하나의 목표가 끝까지
> 도달하게** 만든다 — 반복의 제어 구조(무엇을 관찰하고, 언제 재시도하고,
> 언제 멈추는가)를 설계한다.

## 권장 실행 모델

- **이 스킬(설계)**: **Claude Sonnet 5 이상**. 루프가 고위험(비가역 작업 포함·
  장시간·비용 큰 재시도)이면 **Claude Opus 5 / Fable 5** 권장 — 설계 오류가
  실행에서 반복 횟수만큼 증폭되기 때문이다.
- **루프 실행 모델**: /goal은 현재 세션 모델로 실행된다. 예산 산정(4단계) 시
  세션 모델 기준으로 계산하고, 루프 성격과 세션 모델이 안 맞으면(기계적
  반복인데 Opus, 고위험인데 Haiku) 모델 변경(`/model`)을 함께 권고한다.

## 대상 루프 형태와 /goal의 동작

```
Goal → Observe → Decide → Act → Verify → 성공했는가?
                   ↑                        │
                   └──── No: 수정/재시도 ────┘   Yes → Stop
```

`/goal <조건 텍스트>`는 Claude Code 기본 명령어다: 조건(최대 4,000자)을 걸면
매 턴 판정 모델이 충족 여부를 평가하며 충족까지 루프한다. 즉 **Verify와
Stop 판정은 런타임이 제공한다** — 이 스킬의 일은 조건 텍스트 안에 성공
기준·루프 계약·재시도 규칙·탈출 조건을 압축해 넣는 것이다. `+Nk`는 턴 토큰
목표 지시자이고, 강한 비용 상한은 세션 시작 시 `claude --max-budget-usd`다.

## 원칙 (하드 레일)

1. **판정 없는 설계 착수 금지** — 작업을 받으면 먼저 루프 사이클 구현이
   가능한지 판정한다(절차 0단계). 가능 판정 전에는 인터뷰·설계를 시작하지
   않고, 불가 판정 시 설계 없이 불가 사유를 보고하고 종료한다.
2. **설계 없는 goal 실행 금지** — 이 스킬의 존재 이유다. 성공 기준·탈출
   조건·예산이 확정되기 전에는 /goal 명령어를 제안하지 않는다.
3. **증거 없는 Verify 금지** — 성공 기준마다 외부 검증 가능한 증거(테스트
   출력·diff·상태 조회·렌더 결과)를 명시한다. Agent의 자기보고("됐다")는
   Verify가 아니다. 증거를 정할 수 없는 기준은 성공 기준이 될 수 없다.
4. **탈출 조건은 성공만이 아니다** — SUCCESS(모든 필수 기준 PASS) /
   BLOCKED(외부 조건 — 자격증명·권한·정보 부족; **재시도하지 않고 중단·
   보고**) / FAILED(재시도 상한 안에서 목표 미달) / ESCALATED(권한·판단 경계
   도달 — 사람에게 반환)를 조건 텍스트에 모두 반영한다. 성공만 정의된 루프는
   실전에서 끝나지 못한다.
5. **재시도는 반복이 아니라 수정이다** — 실패 시 원인 분석 후 무엇을 다르게
   할지 결정하고 재시도하게 명시한다. 같은 실패 2회 반복 시 중단·보고.
6. **예산 필수** — 최대 반복 횟수와 `+Nk` 토큰 목표 없는 명령어는 제안하지
   않는다.
7. **루프 하나 = 목표 하나** — 목표가 둘 이상이면 명령어를 나누거나,
   루프 간 연결이 필요하면 design-graph로 승격한다.
8. **복붙 한 줄 원칙** — 최종 산출물은 **코드블록 하나에 담긴 한 줄 명령어**다.
   줄바꿈 없이(터미널 붙여넣기 시 조기 제출 방지), 4,000자 이내로, 코드블록
   안에 명령어 외 다른 텍스트를 섞지 않는다. 설명은 코드블록 밖에 쓴다.

## 절차

### 0. 루프 적합성 판정 (게이트)

설계에 앞서, 사용자가 입력한 작업이 **루프 사이클(Observe → Decide → Act →
Verify → 재시도/종료)로 구현 가능한지** 먼저 검토하고 가능 여부를 판정한다.
아래 네 항목을 모두 통과해야 **가능**이다:

| 판정 항목 | 통과 조건 |
|---|---|
| **종료 상태 정의 가능** | 외부 증거로 판정 가능한 종료 상태를 정의할 수 있다 (취향·감상 등 주관 판정만 가능한 목표는 불가) |
| **관찰 가능** | 매 반복에서 진행 상태를 관찰할 신호(파일·테스트·상태 조회·로그)가 존재한다 |
| **반복이 유효** | 실패 → 수정 → 재시도로 결과가 개선되는 구조다 (한 번 실행으로 끝나는 일회성 작업, 재시도가 무의미한 비가역 작업은 불가) |
| **Agent 실행 가능** | Act가 Agent의 도구·권한 범위 안이다 (매 반복 사람의 물리적 행동·외부 승인 필수인 작업은 불가) |

- **가능** → 판정 결과를 한 줄로 고지하고 1단계(루프 사이클 설계)로 진행한다.
- **불가능** → **불가 판정 메시지와 이유**(어느 항목이 왜 실패했는지)를
  출력하고 설계 없이 종료한다. 가능하면 대안을 한 줄 덧붙인다 — 일회성
  실행으로 충분 / 목표를 검증 가능하게 재정의 / 다중 목표는 분할 또는
  design-graph / 환경 문제는 design-harness.
- 정보 부족으로 판정 자체가 안 되면 지어내지 않고 사용자에게 묻는다.

### 1. Goal 인터뷰 → 성공 기준

사용자에게 묻고 (한 번에 몰아서), 답을 확정한다:

- **목표 → 성공 기준**: 자연어 목표를 검증 가능한 기준 목록으로 변환하고,
  기준마다 **검증 증거**(무엇으로 증명하는가 — 가능하면 실행 명령까지)를
  함께 확정한다.
- **Open-ended 목표**("최대한 개선" 류)에는 Satisficing Condition(충분히
  좋은 상태)을 정의한다 — 더 *할 수 있는* 것과 더 *해야 하는* 것은 다르다.
- **Invariants**: 어떤 반복에서도 절대 하면 안 되는 것 (예: main 직접 push
  금지, 프로덕션 데이터 수정 금지).
- **사람 개입 지점**: 어느 판정에서 멈추고 물어야 하는가?

사용자가 답하지 못하는 항목은 비워 둔다 — 지어내지 않는다. 핵심(성공 기준의
증거)이 빈 채로는 명령어를 제안하지 않는다.

### 2. 단계별 계약 설계

루프의 네 단계를 각각 한 구절로 확정한다 — 조건 텍스트에 그대로 들어간다:

| 단계 | 확정할 것 |
|---|---|
| **Observe** | 무엇을 관찰하는가 (파일·테스트 결과·상태·로그) |
| **Decide** | 관찰 결과 → 행동 선택의 판정 기준 |
| **Act** | 허용된 행동의 범위. Invariant에 걸리는 행동은 원천 배제 |
| **Verify** | 성공 기준별 검증 방법 — 실행 명령까지 구체적으로 (예: `pytest tests/ -x`) |

### 3. 재시도 정책

- **최대 반복 횟수** (기본 권장: 3–5회. 그 이상 필요하면 목표가 너무 크다는
  신호 — 분할을 제안한다)
- **반복 간 수정 규칙**: 실패 시 무엇을 바꾸는가 (가설 수정·범위 축소·접근
  변경)
- **에스컬레이션**: 같은 실패 2회, BLOCKED 감지, Invariant 근접 시 — 중단하고
  현재 상태를 보고한다.

### 4. Budget — 토큰 예산 산정

- **반복 1회 비용 추정**: 소형(단일 파일 수정 + 테스트) ≈ 20–50k / 중형
  (멀티 파일 + 빌드·테스트) ≈ 50–150k / 대형(탐색 + 멀티 파일 + 검증 루프)
  ≈ 150k+
- **토큰 예산** = 반복 1회 비용 × (최대 반복 횟수 + 1), 50k 단위 올림 →
  명령어의 `+<예산>k`가 된다.
- 대형·고위험 루프에는 `claude --max-budget-usd <금액>` 병행을 코드블록
  **밖에서** 안내한다.

### 5. 명령어 조립 + 제안

1–4단계 결과를 아래 구조로 압축해 **한 줄**로 조립한다. 판정 모델이 조건
텍스트만 보고 종료를 판단하므로 **성공 기준(증거 포함)을 맨 앞에** 둔다:

```
/goal <목표 한 줄>. 성공 기준(모두 증거로 검증, 전부 PASS 시에만 완료): (1) <기준>=<검증 명령/증거> (2) <기준>=<증거>. 루프: <Observe>를 관찰 → <Decide 기준>으로 판단 → <Act 범위> 실행 → <Verify 명령>으로 검증. 실패 시 원인 분석 후 접근을 수정해 재시도(최대 N회). 같은 실패 2회·외부 요인 차단·권한 경계 도달 시 중단하고 상태 보고. 금지: <Invariants> +<예산>k
```

제안 전 자가 점검: (a) 한 줄인가 (b) 4,000자 이내인가 (c) 성공 기준마다
증거가 있는가 (d) 반복 상한·중단 조건·`+Nk`가 있는가. 하나라도 실패하면
압축하거나 목표 분할을 제안한다. 통과하면 코드블록 하나로 제시하고, 필요한
사전 조치(모델 변경·`--max-budget-usd`)는 블록 밖에 한 줄로 덧붙인다.

## 산출물이 아닌 것

- **문서를 만들지 않는다** — 산출물은 복붙 명령어 한 줄이다. 설계 근거가
  길어지면 대화로 설명하되 파일로 남기지 않는다.
- 루프를 **실행하지 않는다** — 실행은 사용자가 명령어를 붙여넣는 순간
  /goal 런타임의 몫이다.
- 멀티 루프·루프 간 오케스트레이션을 설계하지 않는다 — design-graph의 몫이다.
- Agent 내부 환경(도구·권한·CLAUDE.md)을 설계하지 않는다 — design-harness의
  몫이다.
