# execute

확정된 플랜을 실행한다. **실행 = 플랜의 작업 목록을 검증 조건까지 포함해 완주하고,
기록과 커밋으로 닫는 것.** 플랜 수정도, 설계 변경도 아니다 — 그런 상황을 만나면
중단하고 보고한다.

## 0. 이 프로젝트를 먼저 읽는다

전역 스킬이므로 어느 레포에서 호출될지 모른다. 프로젝트 지침 파일(`CLAUDE.md`·
`AGENTS.md`)과 표준 검사 명령(통합 게이트)·작업 원장(`kanban.md`·`workstate.md`)·기록
규약·커밋/push 정책을 파악한다. 프로젝트 규약이 있으면 이 스킬의 기본값을 이긴다.

## 인자 — 대상 특정

`$1`은 **실행 대상 문서의 경로**다. 뒤에 재개 지점이 붙을 수 있다.

| 인자 | 동작 |
|---|---|
| `plans/YYYYMMDD-<주제>-plan.md` | 그 플랜을 처음부터 실행 |
| `plans/YYYYMMDD-<주제>-plan.md T-005부터` | 그 작업 ID부터 재개. **앞선 작업이 실제로 끝났는지 커밋·산출물로 확인한 뒤** 시작한다 — 플랜 체크박스만 믿지 않는다 |
| `plans/YYYYMMDD-<대상>-verify-report.md` | 검증 리포트의 **위반 판정 항목**을 작업 목록으로 삼는다. 기대값의 정본은 리포트가 아니라 리포트가 인용한 설계 문서이므로 그 문서를 반드시 읽는다. 발견이 여러 건이고 서로 얽히면 실행하지 말고 `/make-plan <리포트 경로>`를 제안한다 |
| (없음) | `plans/`에서 상태가 `초안`·`중단`인 플랜을 찾아 **후보를 경로째 제시하고 확인받는다.** 임의로 고르지 않는다 |

## 전제 확인 (실행하면 안 되는 경우)

1. **플랜 문서가 없으면 중단** — 없으면 `/make-plan docs/<주제>.md`를 제안한다.
   스킬명만 넘기지 않고 대상 경로까지 준다.
2. **플랜의 "착수 전 사용자 결정"에 응답이 없으면 실행하지 않는다.** 사용자가
   "플랜대로"라고만 했으면 권장안 채택 의사인지 확인한다 — 단 명시적으로 "권장안대로"
   라고 했거나 이 대화에서 이미 답했으면 재질문하지 않는다.
3. **플랜이 참조하는 정본 설계 문서를 읽지 않았으면 먼저 읽는다.** 플랜의 서술은 계약이
   아니다 — 검증 기대값·판정 근거는 항상 설계 문서에서 나온다. 플랜과 설계 문서가
   어긋나면 설계 문서가 이긴다.
4. 작업 원장이 있으면 이 작업의 항목을 특정한다. 없으면 만든다 — 원장에 없는 작업은
   중단되는 순간 사라진다. 항목이 보류 상태면 착수하지 말고 보류 사유가 풀렸는지 먼저
   보고한다.

## 실행 절차

### 1. 스냅샷 선커밋 + 실행 리포트 개설

git 레포면 착수 전 미커밋 변경분을 커밋한다(롤백 스냅샷 — 플랜의 롤백 절이 이것을
전제한다). 워킹트리가 클린해야 작업 단위 revert가 가능하다.

이어서 **첫 작업에 손대기 전에** 실행 리포트를 만든다:
`plans/YYYYMMDD-<주제>-execute-report.md` (날짜는 `date +%Y%m%d`로 확인. `<주제>`는
대상 문서와 같은 주제어).

```markdown
# 실행 리포트 — <주제>

- 상태: **진행 중** (착수 YYYY-MM-DD HH:MM)
- 대상 플랜: plans/YYYYMMDD-<주제>-plan.md
- 정본 설계 문서: <경로들>
- 착수 전 HEAD: <커밋 해시>
- 착수 전 사용자 결정: <각 결정과 채택안 / "권장안 전부 채택">

## 작업 원장

| 작업 | 결과 | 검증 조건 | 커밋 | 비고 |
|---|---|---|---|---|
```

**재개 지점의 정본은 이 파일이다** — 플랜 체크박스도, 커밋 로그도 아니다. 그래서
마지막이 아니라 **착수 시점에** 만든다. 끝에 몰아 쓰는 리포트는 세션이 끊기거나
컨텍스트가 요약되는 순간 통째로 사라지고, 유실이 가장 큰 지점이 바로 실행 사이클이다.

`T-00x부터` 재개인 경우: 같은 날짜의 리포트가 이미 있으면 새로 만들지 말고 **이어
쓴다.** 날짜가 다르면 새 파일을 만들되 머리에 이전 리포트 경로를 적는다.

### 2. 작업 순서 준수

- 플랜의 의존성 그래프 순서대로. **"문서 먼저" 작업이 있으면 반드시 코드보다 먼저** —
  문서 확정 없이 구현하면 검증 기대값의 정본이 없다.
- 각 작업의 검증 조건(체크박스)을 **실행하고 결과를 확인한 뒤** 다음으로 넘어간다.
  "될 것이다"로 넘어가지 않는다.
- 서브에이전트를 쓸 수 있는 런타임이고 플랜이 병렬 구간을 지정했으면 위임한다 —
  디스패치에 **작업 ID + 정본 설계 문서 경로 + 플랜 경로**를 넘긴다. 서로 다른 파일을
  만지는 작업만 병렬로, 같은 파일이 겹치면 순차로.
- **플랜의 기술 리스크는 해당 작업 초입에 실측으로 해소한다.** 실측이 플랜의 가정과
  다르면: 계약과 무관하면 판단 근거를 남기고 진행, 계약이 걸리면 중단·보고.
- git 레포면 작업 단위 원자 커밋. 커밋 메시지에 작업 ID(`T-00x`)를 남긴다.
- **작업 하나가 끝날 때마다 실행 리포트 원장에 한 행을 append한다.** 커밋 직후가 그
  시점이다 — 다음 작업으로 넘어간 뒤에 쓰지 않는다.

| 열 | 채우는 값 |
|---|---|
| 작업 | `T-00x` + 한 줄 요약 |
| 결과 | `완료` / `부분` / `건너뜀` / `중단` — 이 넷 밖의 값을 쓰지 않는다 |
| 검증 조건 | 실제로 돌린 명령과 결과(그린/실패 건수). 안 돌렸으면 `미실행`이라고 쓴다 |
| 커밋 | 해시 7자리. 커밋이 없으면 `없음` |
| 비고 | 플랜 가정이 실측으로 뒤집힌 것, 역검증 결과 |

원장은 **사실만** 적는다. 왜 그렇게 판단했는지는 프로젝트의 작업 노트 규약(devnote 등)
몫이다 — 같은 내용을 두 곳에 두지 않는다.

### 3. 게이트는 역검증까지

새 검사(예산 스크립트, 스키마 검증 등)를 만들거나 확장하면 **일부러 위반을 넣어 실제로
실패하는지 확인**한다 — 통과만 확인하는 검사는 아무것도 못 잡는다.

### 4. 독립 검증 — 산출물 기반으로 배치

플랜에 검증자 역할이 있으면 **수행자와 분리**해 실행한다. 서브에이전트를 쓸 수 있으면
별도 에이전트로 — 디스패치에 **검증 대상 경로 + 정본 설계 문서 경로(§번호) + 산출물
파일 경로**만 넘기고, 구현 의도 설명은 넘기지 않는다(의도를 설명받는 순간 독립 검증이
아니다). 지시에 반드시 포함할 것:

- 검증 대상 소스 수정 금지. 테스트 파일만 작성
- **기대값은 구현 코드가 아니라 정본 설계 문서에서 도출.** 구현이 문서와 다르면 테스트는
  문서 편 — 실패 상태로 제출
- 회색지대는 임의 판정하지 말고 `[미규정]` 표시 + "판정 필요"로 남기게 한다
- **산출물(파일)로 검증 가능하게 시킨다** — 서술 보고는 유실될 수 있다. 보고가 안 오면
  기다리지 말고 산출물을 직접 읽어 판정한다

검증 결과를 받으면: **증상 보고는 신뢰하되 원인 진단은 코드에서 직접 확인한다** — 수정
지점이 달라진다. 위반 판정이 나면 **문서 먼저**: 계약이 이미 함축한 것이면 명문화 추가
후 구현 수정, 계약 자체가 바뀌어야 하면 중단·사용자 확인(설계 재논의 승격).

### 5. 통합 게이트

프로젝트 표준 검사 명령(§0에서 파악한 것)을 1회 실행한다. 전부 그린이어야 완료다.

### 6. 마무리 (순서 고정)

1. **실행 리포트 종결** — 머리의 상태를 `완료 (YYYY-MM-DD)` 또는
   `중단 (YYYY-MM-DD, T-00x까지 / 사유)`로 바꾸고 아래 절을 덧붙인다. **중단으로 끝날 때
   이 절이 가장 중요하다** — 재개할 사람이 읽을 유일한 문서다
   - **통합 게이트 결과** — 돌린 명령과 결과. 못 돌렸으면 그 사유
   - **완료하지 못한 것** — 남은 작업 ID와 각각 무엇이 풀려야 재개되는지
   - **이 사이클이 검증하지 않은 범위** — §7 트리거 판정의 근거가 된다
   - **관련 문서** — 검증 산출물·플랜·설계 문서 경로
2. **작업 원장 갱신** — 아래 §6-1. 기록 규약(devlog 등)이 있으면 그보다 먼저 한다
3. **플랜 문서 머리의 상태 갱신** — `초안` → `완료 (YYYY-MM-DD)`, 중단이면
   `중단 (YYYY-MM-DD, T-00x까지 완료 / 사유)` (어휘 정본은 `/make-plan` §3). 실행 리포트
   경로도 함께 적어 플랜에서 원장으로 갈 수 있게 한다
4. 프로젝트의 기록 규약이 있으면 결정·배제 중심 요약을 남긴다
5. git 레포면 남은 변경분 커밋. **push는 프로젝트의 push 정책을 따르고, 정책이 없으면
   사용자 확인 후**
6. **다음 단계 판정 — `/verify`가 필요한가** (아래 §7)
7. **다음 명령을 보고 마지막 줄에 낸다** (아래 §8)

**중단하는 경우에도 1번은 건너뛰지 않는다.** 오히려 중단이 리포트가 존재해야 하는
이유다 — 정상 종료는 커밋과 게이트가 사실을 남기지만, 중단은 리포트가 없으면 아무것도
남지 않는다.

### 6-1. 작업 원장 갱신 — 있는 프로젝트에서만

| 사이클이 끝난 상태 | 항목 처리 |
|---|---|
| 플랜 완주 + §7 트리거 없음 | 닫는다 |
| 플랜 완주 + §7 트리거 걸림 | "검증 대기"로. 다음 명령을 `/verify <경로>`로 갱신 |
| 플랜에 작업이 남음 | "진행 중" 유지. 다음 명령에 **재개 지점(`T-00x부터`)까지** 적는다 |
| 중단 | "진행 중" 유지 + 무엇이 풀려야 재개되는지 한 줄. 계약 문제로 중단이면 선행 설계 항목을 새로 만든다 |
| 실행 중 새로 발견된 처분 대상 | 새 항목. 프로젝트에 마일스톤 범위 규약이 있으면 범위 밖은 백로그로 |

**항목 없이 끝내지 않는다.** 이번 사이클이 낳은 후속 작업이 원장에 없으면 다음 세션에
존재하지 않는다. 항목에 적는 경로는 쓰기 전에 실제로 연다.

### 7. `/verify` 권고 판정 — 사이클 종료 보고의 마지막

이 사이클의 독립 검증(§4)은 **플랜이 배정한 계약 표면을, 작성 시점에** 검증한다. 그
밖은 구조적으로 못 본다. 아래 트리거 중 **하나라도 걸리면** 종료 보고 끝에
`/verify <검증 대상 경로>`를 **어느 트리거인지와 함께** 적는다. 대상 경로는 트리거가
가리키는 곳이다 — "검증이 못 본 범위"가 곧 대상이므로 `/verify`만 적으면 그 범위가
사라진다.

**하나도 안 걸리면 권장하지 않는다.** 매번 붙이면 신호가 죽어 정작 필요할 때 무시된다.

| 트리거 | 왜 이번 검증이 못 봤나 | 확인 방법 |
|---|---|---|
| **검증 착수 *후에* 계약을 고쳤다** | 테스트는 개정 **이전** 문서에서 도출됐다 — 개정분은 아무도 검증하지 않았다 | 개정 시각 ↔ 검증 착수 시각 |
| **플랜이 검증을 배정하지 않은 절·패키지에 구현이 닿았다** | 검증 범위는 플랜이 배정한 절뿐이다 | 플랜의 검증 명세 ↔ 실제 변경 파일 |
| **플랜에 검증자 역할이 아예 없었다** | 독립 검증이 0회다 | 플랜 §역할 분담 |
| **플랜 밖 수동 변경이 섞였다** | 계약 대조를 거친 적이 없다 | 커밋 로그에 작업 ID 없는 변경 |
| **마지막 사후 감사 이후 오래 지났다** | 줄번호·수치·"현재 ~다" 문장은 쓰일 당시엔 맞았어도 조용히 썩는다 | `ls plans/*-verify-report.md`의 최신 날짜 |

**`/verify`로 해결되지 않는 것은 그렇게 적는다** — 잘못 보내면 두 번 헛돈다.

- **설계 결함 의심** → `/verify`가 아니라 **`/make-design` 재논의**다. 검증은 *"문서 대비
  구현"*을 보므로 **문서 자체가 틀렸으면 그린이 난다.**
- **"실제로 동작하는가"** → 검증 스킬이 아니라 **실사용**이다. 계약 그린과 동작은 다른
  사실이다.

## 8. 다음 명령 (필수)

사이클을 닫든 중단하든, 보고의 **마지막 줄**은 다음 명령이다. 형식은 고정한다:

```
권장 모델 — <opus|sonnet|haiku> · <복잡도 근거 한 줄>
/<스킬명> <대상 파일 경로>
```

- **스킬명만 쓰지 않는다.** `/verify`가 아니라 `/verify packages/providers`다. 대상 없는
  인계가 작업 흐름이 끊기는 지점이고, 실행 사이클은 컨텍스트가 가장 길어 유실도 여기서
  가장 크다.
- 경로는 **프로젝트 루트 기준 전체 상대 경로.** 문서의 일부면 `§번호`, 아직 없는 파일이면
  `(신규)`.
- **경로는 쓰기 전에 실제로 연다.** 존재 확인 없이 기억으로 쓴 경로는 다음 세션을 잘못된
  파일로 보낸다 — `(신규)`가 붙는 경우만 예외다.
- **중단으로 끝날 때가 가장 중요하다** — 재개 지점(`T-00x부터`)과 무엇이 풀려야
  재개되는지를 한 줄로 함께 낸다. 실행 리포트 경로도 함께 흘린다 — 다음 명령만 남고
  원장을 못 찾으면 재개할 때 커밋 로그를 역추적하게 된다.
- **권장 모델을 명령 줄 바로 위에 붙인다.** 판정은 **다음 작업의 복잡도**다 — 열린
  결정을 닫거나 되돌리기 어려운 것을 만들면 상위 모델(예: opus), 계약이 확정돼 있어
  따라가면 되면 중위(sonnet), 판단 없이 기계적으로 끝나면 하위(haiku). 경계에 걸리면
  오류 비용이 큰 쪽 — 특히 설계 결함·계약 위반으로 중단해 `/make-design`으로 넘기는
  경우는 상위다. 현재 세션 모델과 다르면 근거 뒤에 `(/model <모델> 후 실행)`을 붙인다.

| 사이클이 끝난 상태 | 다음 명령 |
|---|---|
| 정상 종료 + §7 트리거 걸림 | `/verify <트리거가 가리키는 대상 경로>` — 어느 트리거인지 함께 |
| 정상 종료, 트리거 없음, 플랜에 남은 작업 있음 | `/execute plans/<같은 플랜>.md T-00x부터` |
| 정상 종료, 플랜 완주 | `/current-status <주제>` — 다음 사이클 판정으로 넘긴다 |
| 계약과 어긋남 발견으로 중단 | `/make-design <정본 문서 경로 §번호>` + 무엇을 판정해야 하는지 한 줄 |
| 설계 결함 발견으로 중단 | `/make-design <정본 문서 경로 §번호>` — **`/verify`가 아니다**(§7: 문서가 틀렸으면 검증은 그린이 난다) |
| 플랜 범위를 벗어나는 작업이 필요 | `/make-plan <설계 문서 경로>` + 범위 확장이 사용자 결정임을 한 줄 |
| 같은 실패 2~3회 반복으로 보고 | 다음 명령 대신 **막힌 지점의 파일 경로**와 선택지를 낸다 — 흐름을 억지로 이어붙이지 않는다 |

(표의 스킬명은 이 마켓플레이스의 interview→make-design→make-plan→execute→verify 체인
기준이다. 프로젝트의 실제 스킬명이 다르면 그 이름으로, 없으면 산문 제안으로 바꾼다.)

## 중단 조건 — 임의로 계속하지 않는다

어느 사유로 멈추든 **보고하기 전에 실행 리포트를 먼저 닫는다**(§6 1번). 보고는 대화에
남고 대화는 사라진다.

- **구현이 정본 설계 문서와 어긋남을 발견** → 코드를 문서에 임의로 맞추지도, 문서를
  코드에 맞추지도 않는다. 중단하고 판정을 보고한다(계약 위반인지, 문서 미규정인지, 문서
  결함인지)
- **설계 결함 발견** → revert가 아니라 설계 재논의로 승격. 사용자 확인 필수
- **플랜 범위를 벗어나는 작업이 필요해짐** → 범위 확장은 사용자 결정. 범위 안에서 마칠
  수 있는 것을 먼저 끝내고 보고한다
- 같은 실패가 2~3회 반복되면 접근을 바꾸기 전에 상황을 보고한다

## 주의

- 새 의존성·새 도구 도입은 플랜에서 결정하지 않았다면 실행 중에도 결정하지 않는다 —
  발견하면 보고.
- 진행 중 실행 리포트 원장을 **그때그때** 이어 쓴다. 특히 실측 결과 — 컨텍스트 요약으로
  유실되기 전에 디스크로 옮긴다. 사이클 끝에 몰아 쓰려고 미뤄둔 기록은 미뤄둔 만큼
  사라진다.

## 전제

interview→make-design→make-plan→execute→verify 체인의 구현 단계. 확정된 플랜이
입력이고, 없으면 `/make-plan`이 먼저다.
