# Make Agents — 목적 맞춤형 에이전트 팀 구성

> **Claude Code 전용 스킬이다** — 절차가 Claude Code의 구성 요소
> (`.claude/agents/`·SKILL.md frontmatter 라우팅·Agent 도구)를 전제한다.
> Codex CLI 사용자는 변형판 [Codex판 SKILL.md](https://github.com/jsj9346/agent-skills/blob/main/codex-plugins/make-agents/skills/make-agents/SKILL.md)를 사용할 것.

> design-* 계열에서의 자리: **design-harness**는 작업 환경(정책·절차·검증·상태)을,
> **design-graph**는 실행 단위의 연결 구조(계약·라우팅·상태 전달)를 설계한다.
> 이 스킬은 **실행자 자체** — 누가, 어떤 지식과 스탠스로, 어떤 모델을 기본값으로
> 일하는가 — 를 만든다. 그래프 설계가 이미 있으면 그 노드 명세를 입력으로 받는다.

> 에이전트는 많을수록 좋은 것이 아니다. 에이전트 하나가 늘 때마다 위임 판단의
> 모호성·컨텍스트 비용·유지보수 부담이 같이 는다. 이 스킬의 성공 기준은
> "몇 명을 만들었나"가 아니라 **"관측된 작업에 맞는 가장 작은 팀을 찾았나"**다.

## 원칙 (하드 레일)

1. **문서 우선, 인터뷰는 갭만** — 워크스페이스 문서(CLAUDE.md·README·docs·
   kanban.md/workstate.md·기존 `.claude/`)를 먼저 읽고, 문서로 답할 수 없는
   항목만 인터뷰로 묻는다. 문서에도 답에도 없는 항목은 비워 둔다 — 지어내지
   않는다. 비워진 항목이 많을수록 팀은 작아지는 게 맞다.
2. **역할 단일성** — 에이전트 하나 = 책임 하나. 두 에이전트의 description이
   같은 작업에 매칭되면 자동 위임이 흔들리므로 결함으로 보고 병합한다.
   (Anthropic 서브에이전트 가이드라인: description은 위임 판단의 유일한 입력이다.)
3. **관측 근거** — 에이전트는 (a) 이 프로젝트에서 **관측된 반복 작업**, 또는
   (b) 사용자가 **명시한 요구**에만 만든다. "혹시 몰라서"는 근거가 아니다.
   팀 상한 기본 **5개**, 초과는 에이전트마다 사용자 승인을 따로 받는다.
4. **최소 도구 권한** — `tools`는 allowlist로 역할에 필요한 것만 준다.
   읽기·분석 역할이면 Write/Edit를 주지 않는다. 생략(전체 도구 상속)은
   범용 워커에만 허용하고 이유를 적는다.
5. **모델은 역할이 정한다** — §4 매트릭스(난이도 × 오류 비용)로 배정하고,
   배정 근거를 파일에 주석으로 남긴다. 애매하면 낮은 티어를 고른다 — 올리는
   비용이 내리는 비용보다 싸다. 모델 교체·신모델 출시 때 주석만 재검토하면
   되게 한다.
6. **라우팅은 강제층 한 곳에** — 스킬→에이전트 연결의 정본은 SKILL.md
   frontmatter(`context: fork` + `agent:`)다. 같은 룰을 CLAUDE.md나 별도
   라우팅 문서에 중복 기재하지 않는다 (역할 단일성). fork가 불가한 스킬만
   예외적으로 스킬 본문의 위임 지시를 쓴다 (§5).
7. **토대 검증** — "런타임이 이 필드를 지원한다/안 한다"는 추정 금지. 이번
   세션에서 문서·실동작으로 확인한 것만 쓰고, 확인 못 한 것은 "미확인"으로
   표기한다. 버전 의존 기능(예: fork 스킬의 `background: false`는 v2.1.218+)은
   버전을 병기한다.
8. **승인 후 생성** — 팀 매니페스트 제시 → 사용자 승인 → 파일 생성.
   기존 스킬의 frontmatter를 수정할 때는 diff를 먼저 보여준다.

## 절차

### 1. 워크스페이스 스캔 (인벤토리)

셋을 **실제로 읽고** 목록화한다:

- **프로젝트 문서**: CLAUDE.md·README·docs/·kanban.md/workstate.md·설계 문서.
  여기서 목적·도메인 용어·반복 작업·품질 기준을 추출한다 — 에이전트의 도메인
  지식 섹션(§3)의 원재료다.
- **기존 실행자**: `.claude/agents/`(있다면), `.claude/skills/`·commands.
  각 항목의 역할을 한 문장으로 적어 역할 목록을 만든다 — 역할 중복 검사의
  기준선이다. 기존 에이전트가 있으면 이 스킬은 **진단 모드**를 겸한다:
  역할 겹침·모델 과잉/과소·죽은 라우팅을 함께 보고한다.
- **런타임 기본기**: 내장 에이전트(Explore·Plan·general-purpose 등)가 이미
  하는 일. 내장으로 충분한 역할은 새로 만들지 않는다.

### 2. 갭 인터뷰 (부족할 때만, 한 번에 몰아서)

문서 스캔으로 답하지 못한 항목만 묻는다:

- **목적**: 이 워크스페이스에서 반복될 작업의 유형은 무엇인가?
- **실패 모드**: 어떤 작업이 잘못되면 가장 아픈가? (→ 그 역할의 모델 티어와
  성격이 여기서 결정된다)
- **우선순위**: 품질 / 비용 / 속도 중 무엇이 중요한가? (→ 모델 배정의 기울기)
- **라우팅 대상**: 어떤 스킬 호출을 에이전트에 연결하고 싶은가?
- **팀 상한**: 기본 5를 바꿀 것인가?

### 3. 팀 설계 — 역할 분해

작업 유형을 역할로 분해하고, 역할마다 다음 6항목을 확정한다:

| 항목 | 규칙 |
|---|---|
| **name / description** | description은 **위임 트리거 조건**을 명시한다 — "~할 때 사용. ~요청 시 위임." 형태. Claude의 자동 위임이 이 필드만 보고 판단한다 |
| **도메인 지식** | §1에서 추출한 **이 프로젝트의 실제** 규칙·용어·파일 위치·품질 기준. 일반론("좋은 코드를 작성한다") 금지 |
| **성격·태도** | 역할에서 **기능적으로 도출** — 리뷰어=회의적·반증 지향, 탐색가=발산적·가설 다산, 문서화=보수적·원문 충실. 장식용 페르소나는 만들지 않는다 |
| **tools** | 최소 allowlist (원칙 4) |
| **model** | §4 매트릭스 + 근거 주석 |
| **출력 계약** | 호출자에게 무엇을 어떤 형태로 돌려주는지 한 문단. fork 라우팅될 에이전트는 필수 — 결과만 반환되기 때문이다 |

생성 파일 스펙 (`.claude/agents/<name>.md`) — 공식 지원 필드만 쓴다
(`name`·`description`·`tools`·`disallowedTools`·`model`·`permissionMode`·
`skills`·`memory`·`maxTurns` 등, 이번 세션에서 확인된 것 기준):

```markdown
---
name: code-reviewer
description: 코드 변경 후 버그·회귀 리뷰가 필요할 때 사용. PR 리뷰, diff 검토 요청 시 위임.
tools: Read, Grep, Glob, Bash
model: opus   # 오류 비용 큰 판단 역할 — §4
---
# 역할        ← 책임 한 문장 + 하지 않는 것
# 도메인 지식  ← 이 프로젝트의 실제 규칙·구조·용어
# 성격·태도   ← 역할에서 도출된 작업 스탠스
# 작업 방식   ← 절차와 자체 검증 기준
# 출력 계약   ← 호출자에게 돌려주는 형태
```

### 4. 모델 배정 매트릭스

판정 기준은 **작업 난이도 × 오류 비용**이다. 모델명은 예시이며, 배정 시점에
사용 가능한 티어를 확인해 맞춘다 (원칙 7):

| 역할 특성 | 티어 | 예 |
|---|---|---|
| 대량·기계적·저판단 (분류·포맷·로그 정리) | 최소 (`haiku`) | 데이터 정리 |
| 일반 구현·검색·문서화 | 표준 (`sonnet`) | 구현 워커, 탐색가 |
| 오류 비용이 큰 판단 (설계·리뷰·보안) | 상위 (`opus`) | 리뷰어, 아키텍트 |
| 최고 난도 추론 (계정에서 가능할 때만) | 최상위 (`fable`) | 핵심 의사결정 |

- 사용자의 우선순위(§2)가 비용이면 한 티어 아래에서 시작해 실패가 관측될 때
  올린다. 품질이면 반대로.
- `model`을 생략하면 세션 모델을 상속한다 — "항상 호출자와 같은 모델이어야
  하는" 역할만 생략을 쓰고 그 이유를 적는다.

### 5. 라우팅 설계 — 스킬 하나에 판정 하나

라우팅 대상 스킬마다 판정한다:

```
이 스킬은 대화 히스토리 없이 독립 실행 가능한가?
├─ 예 → [정본] SKILL.md frontmatter:
│         context: fork
│         agent: <에이전트명>          # .claude/agents/의 name
│         background: false            # 결과를 그 턴에서 써야 할 때 (v2.1.218+)
└─ 아니오 (대화 맥락 필요) → fork 불가.
          스킬 본문에 "Agent 도구로 <에이전트명>에게 위임" 지시를 넣는
          지침 라우팅으로 대체하고, 왜 fork가 아닌지 한 줄 기록한다.
```

fork 라우팅 적용 전 검사 (공식 문서 확인 사항):

- fork된 스킬 본문은 **실행 가능한 지시문**이어야 한다 — 수동적 가이드라인만
  있으면 빈 결과가 돌아온다. 조건 미달이면 라우팅 전에 본문 재작성을 제안한다.
- fork는 대화 히스토리를 보지 못한다 — 스킬이 필요로 하는 입력은 스킬 인자나
  본문에 명시적으로 흘러들어가야 한다.
- SKILL.md의 `model:` 필드는 fork 시 서브에이전트 모델을 덮어쓴다 — 에이전트
  frontmatter의 model과 이중 지정하지 않는다 (정본은 에이전트 쪽).

### 6. 매니페스트 제시 → 승인 → 생성

생성 전에 표로 제시하고 승인을 받는다:

| 에이전트 | 역할 (한 문장) | model (근거) | tools | 라우팅되는 스킬 | 근거 (관측/요구) |
|---|---|---|---|---|---|

함께 보고한다:

- **팀 크기 대비 수치**: "상한 5, 신규 3".
- **역할 중복 검사 결과**: 내장 에이전트·기존 에이전트와 겹침 없음, 또는
  병합·제거 내역.
- **만들지 않은 역할**과 이유 (근거 부족·내장으로 충분·상한 초과). 관측이
  쌓이면 다시 꺼낼 수 있게 보류 목록으로 남긴다.

승인 후 `.claude/agents/*.md`를 생성하고 라우팅 대상 스킬의 frontmatter를
수정한다 (수정 diff 선제시 — 원칙 8).

### 7. 검증 — 위임 시나리오

에이전트마다 최소 1개 시나리오를 실제로 호출해 확인한다:

- **라우팅 검증**: 연결된 스킬을 호출 → 지정 에이전트에서 실행되고 출력
  계약대로 결과가 돌아오는가.
- **자동 위임 검증**: description의 트리거 조건에 해당하는 요청을 던져 →
  의도한 에이전트로 위임되는가. 다른 에이전트와 경합하면 description을
  상호 배타적으로 수정한다.
- 실패한 시나리오는 수정 후 재검증한다 — 검증 없이 "생성 완료"로 보고하지
  않는다.

## 과잉 팀 신호

설계안이나 기존 구성에서 다음이 보이면 병합·제거 대상으로 보고한다:

- description이 겹치거나, 한 요청에 두 에이전트가 매칭된다.
- 내장 에이전트(Explore·Plan·general-purpose)로 충분한 역할을 다시 만들었다.
- 라우팅되는 스킬도, 위임 요청 이력도 없는 에이전트가 있다.
- 단순 작업 역할에 상위 티어 모델이 배정돼 있다 (근거 주석 없음).
- 에이전트 본문이 프로젝트 지식 없이 일반론으로만 채워져 있다.
- 팀 크기가 상한을 넘는데 개별 승인 기록이 없다.

## 산출물이 아닌 것

- 이 스킬은 도메인 지식을 대신 공급하지 않는다 — 에이전트의 지식 섹션은
  워크스페이스 문서와 사용자의 답에서만 온다. 원재료가 없으면 팀도 얇아지는
  게 맞다.
- 워크플로우 오케스트레이션(누가 누구에게 무엇을 넘기는가)은 만들지 않는다 —
  그것은 design-graph의 일이다. 이 스킬은 노드(실행자)까지만 만든다.
- 작업 환경(정책·훅·권한 체계)은 만들지 않는다 — 그것은 design-harness의
  일이다. 에이전트에 필요한 permissionMode 지정까지만 다룬다.
