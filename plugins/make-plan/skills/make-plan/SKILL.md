# make-plan

확정된 설계를 **실행 가능한 플랜 문서**로 변환한다. 플랜 = 작업을 순서·검증 조건과
함께 배열한 것. 설계(무엇을 만들지)와 플랜(어떻게 실행할지)을 혼동하지 않는다 —
계약을 새로 정해야 하면 `/make-design`으로 되돌린다.

## 0. 이 프로젝트를 먼저 읽는다

전역 스킬이므로 어느 레포에서 호출될지 모른다. 프로젝트 지침 파일(`CLAUDE.md`·
`AGENTS.md`)과 표준 검사 명령(테스트·린트·통합 게이트)·작업 원장(`kanban.md`·
`workstate.md`)·플랜 저장 규약을 파악한다. 프로젝트 규약이 있으면 이 스킬의 기본값을
이긴다.

## 인자 — 대상 특정

`$1`은 **이 플랜이 구현할 정본 설계 문서의 경로**다.

| 인자 | 동작 |
|---|---|
| `docs/<주제>.md` (설계 문서) | 그 문서를 계약으로 삼아 플랜을 짠다 |
| `plans/YYYYMMDD-<대상>-verify-report.md` | 검증 발견 목록을 작업 목록의 입력으로 삼는다. **계약은 여전히 리포트가 인용한 정본 문서**이므로 그 문서도 함께 읽는다 |
| (없음) | 작업 원장에서 후보를 뽑아 **경로째 제시하고 확인받는다.** 정본을 특정하지 못한 채 플랜을 짜지 않는다 |

## 전제 확인 (플랜을 짜면 안 되는 경우)

- **정본 설계 문서가 없으면 중단** — "무엇을 만드는지"의 계약이 확정돼 있어야 한다.
  없으면 `/make-design docs/<주제>.md (신규)`를 먼저 제안한다 — 스킬명만 넘기지 않고
  대상 경로까지 준다.
- 대상 설계 문서에 **미결 절이 있으면**: 각 미결이 이 플랜의 블로커인지 판정해 리스크
  절에 명시한다. 블로커면 플랜 착수 전 결정 항목으로 올린다.

## 절차

### 1. 컨텍스트 수집

대상 설계 문서 전체 + 그 문서가 참조하는 상위 정본(아키텍처 원칙·기술 스택 문서) +
작업 원장의 관련 항목. 이미 세션에서 파악된 정보는 재질문하지 않는다. 추정한 부분은
`[추정]` 표시 + 착수 전 확인 항목으로 올린다.

### 2. 날짜 확인 후 파일 생성

```bash
date +%Y%m%d
```

**컨텍스트의 날짜를 믿지 말고 실행해서 확인한다** (자정 경계에서 어긋난다). 저장 위치:

```
plans/YYYYMMDD-<주제>-plan.md
```

(`plans/`가 없는 프로젝트는 만든다. 플랜을 공개 레포에 올릴지는 프로젝트의 `.gitignore`
규약을 따른다.)

### 3. 문서 구조 (이 순서 고정)

**문서 머리(제목 바로 아래 고정)** — 상태·작성일·정본 경로를 든다. 상태 어휘는 셋으로
닫는다: `초안`(착수 전 결정이 남았으면 `초안 — 착수 전 결정 N`으로 병기) /
`완료 (YYYY-MM-DD)` / `중단 (YYYY-MM-DD, T-00x까지 / 사유)`. **상태 전이는 `/execute`가
한다** — 이 어휘가 "미완 플랜 찾기"의 판독 기준이다.

1. **개요** — 목표(플랜의 종점을 한 문장으로), 전제한 기술 스택(기확정 참조만 — 새 도구
   도입은 플랜에서 결정하지 않는다), 제약 조건, 현재 상태, 성공 기준(명령어로 검증
   가능하게 — interview 결정 기록이 있으면 그 `## 성공 기준`이 원천이다)
2. **작업 목록** — P0(없으면 동작 불가)/P1(핵심)/P2(품질)/P3(부가). 표: ID(`T-00x`)·
   작업명(동사로 시작)·선행·산출물. **15개 초과 시 분할 제안**
3. **역할 분담** — 서브에이전트를 쓸 수 있는 런타임이면 수행자·검증자를 나눈다.
   **수행자와 검증자 분리 필수** — 검증자는 구현이 아니라 **정본 설계 문서를 보고**
   테스트를 작성한다. 프로젝트에 표준 에이전트 로스터가 있으면 그 이름으로 배정하고,
   즉석 역할을 발명하지 않는다
4. **상세 작업 명세** — 작업별 내용·산출물·검증 조건(체크박스, **복붙 실행 가능한 명령
   우선. "정상 동작 확인" 금지** — 잴 수 없는 검증 조건은 검증하지 않은 것과 같다)
5. **의존성 그래프** — 텍스트 다이어그램 + 병렬 가능 구간 + 임계 경로
6. **검증 실행 계획** — 수행자 1차 → 검증자 독립 재검증 → 통합 게이트 1회
7. **롤백 플랜** — 스냅샷 시점(착수 전 미커밋 변경분 선커밋 여부 포함), 트리거, 명령어.
   **설계 결함 발견은 revert가 아니라 설계 재논의로 승격**(사용자 확인 필수)임을 명시
8. **리스크 및 미결** — 기술 불확실성(어느 작업에서 실측할지 명시), `[추정]` 항목,
   **착수 전 사용자 결정 목록**

### 4. 고정 관례 (플랜에 반드시 반영)

- **"계약과 어긋나면 문서 먼저"** — 구현 중 정본 문서와 어긋남 발견 시 코드를 임의로
  맞추지 않고 중단·보고. 계약 변경은 결정 기록 + 문서 수정이 선행
- **통합 게이트는 프로젝트 표준 검사 명령을 참조**한다(`package.json`의 check 스크립트
  등). 플랜에 개별 명령을 복제해 열거하지 않는다 — 게이트가 늘 때마다 낡는다
- **설계 문서의 예산·불변 조건은 검증 조건으로 번역** — 예: 의존성 예산 → 검사 명령,
  불변 조건 → 테스트 1:1 매핑 작업
- **작업 단위 원자 커밋, push는 사용자 확인 후** — 마지막 작업은 항상 "기록 + 커밋 준비"

### 5. 독립 검토 — 전달 전에

플랜 초안이 완성되면 **사용자에게 전달하기 전에** 독립 검토를 거친다. 서브에이전트를
쓸 수 있으면 읽기 전용 검토자에게 **플랜 초안 경로 + 정본 설계 문서 경로만** 넘긴다 —
작성 의도 설명을 함께 넘기면 독립 검토가 아니다. 서브에이전트가 없으면 정본 문서를
다시 열고 플랜을 역방향으로 대조한다(각 작업이 어느 계약 조항에서 왔는지).

발견 처리:

- **블로커** — 플랜에 반영하고 반영 내용을 전달 보고에 한 줄씩 남긴다. 반영하지 않기로
  했으면 그 판단을 **착수 전 사용자 결정**으로 올린다 — 말없이 기각하지 않는다
- **보강** — 반영 여부를 판단하되, 안 한 것은 플랜의 리스크 절에 남긴다
- **설계 재논의 후보** — 플랜 발견과 섞지 않고 별도 보고한다(`/make-design` 제안 대상)

### 6. 마무리

- 플랜 경로와 **착수 전 사용자 결정 목록**을 본문에 요약한다 — 결정 없이 실행에
  들어가지 않는다. 독립 검토 결과(블로커 몇 건 반영, 미반영 판단)도 함께.
- 작업 원장이 있으면 갱신 — 이 작업의 항목을 "진행 중"으로 옮기고 다음 명령을
  `/execute plans/YYYYMMDD-<주제>-plan.md`(방금 만든 실제 파일명)로 적는다. 플랜을
  분할했으면 **단계마다 항목 하나** — 플랜의 `T-00x`를 항목으로 만들지는 않는다(원장
  항목은 플랜보다 크다).
- 프로젝트의 기록 규약이 있으면 요약을 남긴다. **플랜 경로를 반드시 포함한다** — 경로
  없이 "플랜 승인"만 적으면 다음 세션이 어느 플랜인지 다시 찾는다.
- **다음 명령을 보고 마지막 줄에 낸다** (아래 §다음 명령)

## 다음 명령 (필수)

플랜을 내든 중단하든, 보고의 **마지막 줄**은 다음 명령이다. 형식은 고정한다:

```
권장 모델 — <opus|sonnet|haiku> · <복잡도 근거 한 줄>
/<스킬명> <대상 파일 경로>
```

- **스킬명만 쓰지 않는다.** `/execute`가 아니라 `/execute plans/20260810-core-plan.md`다.
  방금 만든 플랜이면 실제 생성한 파일명을 그대로 쓴다(날짜·주제 슬러그 포함).
- 경로는 **프로젝트 루트 기준 전체 상대 경로.** 문서의 일부면 `§번호`, 아직 없는 파일이면
  `(신규)`.
- **경로는 쓰기 전에 실제로 연다.** 플랜이 드는 정본·입력 리포트 경로는 특히 그렇다 —
  플랜은 그 경로를 실행 사이클에 그대로 넘긴다.
- **권장 모델을 명령 줄 바로 위에 붙인다.** 판정은 **다음 작업의 복잡도**다 — 방금 만든
  플랜을 넘길 때는 플랜 자체가 근거다: 작업이 여러 패키지에 걸치거나 불확실성 메모가
  있으면 상위 모델(예: opus), 태스크가 명확하면 중위(sonnet), 기계적이면 하위(haiku).
  경계에 걸리면 오류 비용이 큰 쪽. 현재 세션 모델과 다르면 근거 뒤에
  `(/model <모델> 후 실행)`을 붙인다.

| 플랜 작성이 끝난 상태 | 다음 명령 |
|---|---|
| 플랜 확정, 착수 전 결정 없음 | `/execute plans/YYYYMMDD-<주제>-plan.md` |
| 착수 전 사용자 결정이 남음 | 같은 줄을 내되 **결정 목록을 그 위에** 두고, "결정에 답한 뒤 이 명령"임을 한 줄로 |
| 정본 설계 부재로 중단 | `/make-design docs/<주제>.md (신규)` |
| 설계 문서의 미결이 블로커 | `/make-design docs/<문서>.md §<미결 번호>` |
| 15개 초과로 플랜을 분할함 | 1단계 플랜 경로로 `/execute plans/...` — **나머지 단계의 파일명도 함께 적어** 어디까지가 이번 사이클인지 보이게 한다 |

(표의 스킬명은 이 마켓플레이스의 interview→make-design→make-plan→execute→verify 체인
기준이다. 프로젝트의 실제 스킬명이 다르면 그 이름으로, 없으면 산문 제안으로 바꾼다.)

## 주의

- **플랜은 실행하지 않는다.** 이 스킬의 산출물은 문서다. 실행은 사용자 승인 후
  `/execute`가 한다.
- 작업 하나가 실행 주체 기준 반나절을 넘길 것 같으면 더 쪼갠다.
- 이전 플랜(`plans/`)이 있으면 겹치는 범위를 확인한다 — 같은 작업을 두 플랜이 소유하면
  어느 쪽이 정본인지 알 수 없어진다.

## 전제

interview→make-design→make-plan→execute→verify 체인의 계획 단계. 확정된 설계 문서가
입력이고, 없으면 `/make-design`이 먼저다.
